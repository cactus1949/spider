# 广东电力交易数据智能采集系统 — 多模式部署方案

> 文档编号：01
> 适用项目：广东电力交易数据智能采集系统（spider-gd）
> 关键词：U-Key、专网（pm.gd.csg.cn）、钉钉远程控制、Agent 集成、离线缓存

---

## 1. 文档概述

### 1.1 为什么需要多种部署模式？

广东电力交易数据采集系统的核心数据源 `pm.gd.csg.cn` 属于**电力交易中心专网**，必须通过电力公司发放的 **U-Key（USB 随身 WiFi）** 才能接入。U-Key 插入电脑后，电脑通过 WiFi 连接专网，**与互联网物理/逻辑隔离**。

但是系统还需要以下**外网能力**：

- **钉钉远程控制**：运维人员远程登录、查看运行状态、紧急干预；
- **Agent 集成**：将采集的数据上传到企业内部数据中台 / LLM Agent 服务；
- **OTA 升级**：远程下发爬虫脚本更新、规则升级；
- **告警推送**：异常情况下钉钉/企业微信通知。

#### 现场环境的不确定性

实际部署时，现场条件**充满不确定性**：

| 现场情况 | 出现频率 | 影响 |
| --- | --- | --- |
| 有现成的有线网口可用 | 中 | 最理想，可走模式 A |
| 仅有 WiFi 覆盖（无有线网口） | 高 | 需要模式 B 或 C |
| 既无有线、WiFi 信号也差 | 中 | 必须依赖 4G 网卡或模式 D |
| 现场严禁外网接入（仅允许 U-Key） | 低 | 强制模式 D |
| 网络管理严格、需 IT 报备开通 | 高 | 短期内只能走模式 D |

> **结论**：单一部署方案无法覆盖所有现场。必须设计**四种递进式部署模式 + 自动降级机制**，让系统能在任何现场快速落地。

### 1.2 设计原则

1. **核心爬虫代码与部署模式解耦**：所有模式共享同一套 `spider-core`；
2. **多配置文件驱动**：每种部署模式对应一个独立配置文件，运行时通过命令行参数切换：
   ```bash
   python main.py --config configs/mode_d_offline.yaml
   python main.py --config configs/mode_a_wired.yaml
   ```
   配置文件目录结构：
   ```
   configs/
   ├── mode_a_wired.yaml        # 单机+有线
   ├── mode_b_wireless.yaml     # 单机+USB无线/4G
   ├── mode_c_dual.yaml         # 双机方案
   ├── mode_d_offline.yaml      # 纯离线保底
   └── common.yaml              # 公共配置（路径、常量等）
   ```
   - 每个 `mode_*.yaml` 仅放该模式的差异配置（网络接口、模式开关等）；
   - **`common.yaml` 集中管理所有模式共用的配置**：数据存储根路径、日志路径、平台域名（`pm.gd.csg.cn`）、台账模板路径、压缩包命名规则、超时与重试参数等，方便统一查找和修改；
   - 启动时框架先加载 `common.yaml`，再用 `--config` 指定的模式文件覆盖/合并，得到最终配置。
3. **保底兜底**：模式 D（纯离线）必须内置，作为最后一道防线；
4. **降级自动化（最低保障线优先）**：
   - **最低保障线**：不管什么情况，**只要 U-Key 插上能访问交易平台，数据就必须爬下来存到本地**——这是系统不可妥协的底线；
   - 外网通信（钉钉远程、Agent 推送、数据上传）属于**锦上添花**，不是必需，外网失败绝不能影响本地采集；
   - 路由失败 / 外网失联 → 自动切换离线缓存模式，本地存储路径在 `common.yaml` 中预设并被所有模式共用，确保任意模式下数据都落到同一根目录、便于统一管理。
5. **硬件最小化**：能用 1 台机器解决，不上 2 台。

## 2. 四种部署模式

### 模式 A：单机 + 有线网络（最优方案）

#### 2.A.1 拓扑图

```
                 ┌────────────────────────────┐
                 │   电力交易专网              │
                 │   pm.gd.csg.cn / 10.x.x.x  │
                 └─────────────▲──────────────┘
                               │ WiFi（U-Key 加密信道）
                               │
   ┌───────────────────────────┴────────────────────────────┐
   │                Windows 采集机                           │
   │                                                        │
   │   [USB 口] ── U-Key ──► WLAN 网卡（接入专网）         │
   │                            │                          │
   │                            ▼                          │
   │   [爬虫进程 spider-core] ──► 抓取交易数据             │
   │                            │                          │
   │   [钉钉客户端 / Agent] ────► 通过有线网卡走外网        │
   │                            ▲                          │
   │   [以太网口] ── 网线 ──► 公司路由器 ──► Internet      │
   └────────────────────────────────────────────────────────┘
```

#### 2.A.2 工作原理

- **U-Key WiFi 接口**：默认网关指向专网网关，**仅路由 `pm.gd.csg.cn` 等专网网段流量**；
- **有线网卡**：作为**默认外网出口**，承担钉钉、Agent 上传、Windows Update 等一切互联网流量；
- 通过 Windows 路由表手动指定专网域名/IP 段走 WLAN，其余走有线，实现**双网卡分流**。

#### 2.A.3 路由配置原理

Windows 默认行为：metric 较低的网卡作为默认网关。U-Key WiFi 接入专网后，往往会抢占默认路由，导致外网流量也被强制走 WiFi（专网拒绝转发，外网就断了）。

**解决思路**：

1. 提高 WLAN 网卡的接口跃点（metric），使其**不**做默认网关；
2. 显式添加 **专网静态路由**，指定下一跳为 WLAN 网关；
3. 有线网卡保留默认网关，承担外网流量。

#### 2.A.4 PowerShell 配置命令

```powershell
# ===== 1. 查看网卡接口索引 =====
Get-NetAdapter | Format-Table Name, ifIndex, Status, MacAddress, LinkSpeed

# 假设：Ethernet (有线)  ifIndex = 12
#       Wi-Fi   (U-Key) ifIndex = 18

# ===== 2. 提高 WLAN 跃点，避免抢占默认路由 =====
Set-NetIPInterface -InterfaceIndex 18 -InterfaceMetric 100

# 有线网卡保持低跃点（默认外网出口）
Set-NetIPInterface -InterfaceIndex 12 -InterfaceMetric 10

# ===== 3. 添加专网静态路由（关键）=====
# 假设专网网段为 10.0.0.0/8，专网网关（U-Key 分配）为 192.168.43.1
route -p add 10.0.0.0 mask 255.0.0.0 192.168.43.1 metric 1 if 18

# 如已知具体目标 IP（pm.gd.csg.cn 解析后的 IP），可只加单条主机路由：
# route -p add 218.x.x.x mask 255.255.255.255 192.168.43.1 metric 1 if 18

# ===== 4. 验证 =====
route print | Select-String "10.0.0.0|0.0.0.0"
ping pm.gd.csg.cn          # 应走 WLAN
ping www.baidu.com         # 应走有线
tracert pm.gd.csg.cn       # 确认下一跳是 192.168.43.1
```

> ⚠️ 实际专网网段、网关 IP、域名需向电力交易中心 IT 部门确认。

#### 2.A.5 硬件需求

| 项目 | 规格 | 数量 |
| --- | --- | --- |
| Windows 主机 | Win10/Win11，4 核 8GB 内存以上 | 1 台 |
| 千兆有线网口 | RJ45 | 1 个 |
| USB 2.0/3.0 端口 | 用于 U-Key | ≥1 个 |
| U-Key | 电力交易中心配发 | 1 个 |
| 网线 | Cat5e 及以上 | 1 根 |

#### 2.A.6 优缺点

✅ **优点**
- 部署最简单，只需一台机器
- 网络最稳定，有线带宽充足
- 钉钉/Agent 实时在线，可即时干预

❌ **缺点**
- 强依赖现场有线网口
- 路由配置稍复杂，需 IT 协助
- 一旦专网域名变更，路由要重配

### 模式 B：单机 + USB 无线网卡 / 4G 网卡

#### 2.B.1 拓扑图

```
                 ┌────────────────────────────┐
                 │   电力交易专网              │
                 └─────────────▲──────────────┘
                               │ WiFi
   ┌───────────────────────────┴────────────────────────────┐
   │                Windows 采集机                           │
   │                                                        │
   │   [USB 口 1] ── U-Key ──► 内置 WLAN 网卡（专网）       │
   │   [USB 口 2] ── 4G 网卡 / USB WiFi ──► 外网            │
   │                            │                          │
   │   [spider-core] ◄──── 专网                             │
   │   [钉钉/Agent]  ◄──── 外网（4G/WiFi）                  │
   └────────────────────────────────────────────────────────┘
                               │
                               ▼
                          Internet
```

#### 2.B.2 适用场景

- 现场**无有线网口**或网口被锁定；
- 仅有访客 WiFi（与办公网隔离）；
- 临时驻场 / 出差短期采集；
- 客户机房不允许接入自带网线。

#### 2.B.3 硬件需求

| 选型 | 推荐型号 | 价格区间 | 特点 |
| --- | --- | --- | --- |
| **USB WiFi 适配器** | TP-Link TL-WN726N / 小米随身 WiFi | ¥40 ~ ¥80 | 便宜，但需现场 WiFi 覆盖 |
| **USB 4G 网卡（推荐）** | 华为 E3372h-320 / 中兴 MF833V | ¥150 ~ ¥300 | 独立网络，最稳定 |
| **USB 5G 网卡** | 华为 5G CPE Pro 系列（USB） | ¥800+ | 高带宽，成本高 |

> **强烈推荐 4G 网卡**：避免与 U-Key WiFi 的驱动冲突，独立网络更可控。

#### 2.B.4 路由配置

逻辑与模式 A 完全相同，仅需把"有线网卡"换成"4G/USB WiFi 网卡"作为默认外网出口：

```powershell
# 假设：4G 网卡 ifIndex = 22, U-Key WLAN ifIndex = 18

Set-NetIPInterface -InterfaceIndex 22 -InterfaceMetric 10    # 4G 默认外网
Set-NetIPInterface -InterfaceIndex 18 -InterfaceMetric 100   # U-Key 不抢默认

route -p add 10.0.0.0 mask 255.0.0.0 192.168.43.1 metric 1 if 18
```

#### 2.B.5 注意事项 ⚠️

1. **双 WiFi 驱动冲突**：Windows 对同时启用两个 WLAN 网卡支持有限，部分驱动会互相禁用。**首选 4G 网卡（识别为以太网/RNDIS 设备）**；
2. **4G 流量套餐**：建议选择物联网定向流量卡（10~30 元/月，30GB+），避免天价漫游费；
3. **信号强度**：机房深处 4G 信号可能弱，需配合 USB 延长线把网卡放到窗边；
4. **APN 配置**：物联网卡通常需手动配 APN，可在 Windows "蜂窝网络"设置中填写。

#### 2.B.6 优缺点

✅ **优点**
- 摆脱有线网络依赖，部署灵活
- 4G 方案与办公网完全隔离，安全合规
- 出差/临时部署友好

❌ **缺点**
- 4G 流量有月度成本
- USB 口被占用 2 个
- 双 WiFi 方案有驱动冲突风险
- 信号不稳定时需重试

### 模式 C：双机方案

#### 2.C.1 拓扑图

```
   ┌──────────────────────────┐         ┌──────────────────────────┐
   │   爬虫机（专网）          │         │   联网机（外网）          │
   │                          │         │                          │
   │   [USB] ── U-Key ──►WLAN │         │   [USB] ── 4G/USB WiFi   │
   │                          │         │             或 [LAN]     │
   │   [spider-core]          │         │   [钉钉客户端]            │
   │   [本地 SQLite]          │         │   [Agent / 调度器]        │
   │   [REST API Server]      │         │   [REST API Client]      │
   │              ▲           │         │              ▲           │
   │   [LAN 网口] │           │◄───网线──►│ [LAN 网口]  │           │
   │   192.168.100.10         │  直连   │   192.168.100.20         │
   └──────────────────────────┘         └──────────────────────────┘
                                                       │
                                                       ▼
                                                  Internet
```

#### 2.C.2 角色分工

| 机器 | 网络 | 职责 |
| --- | --- | --- |
| **爬虫机** | 仅专网（U-Key） | 跑 `spider-core`、本地 SQLite 缓存、对内提供 REST API |
| **联网机** | 仅外网（4G/有线） | 跑钉钉、Agent、调度器、定时拉取爬虫机数据上传 |

#### 2.C.3 两机通信方案

##### 方案 ①：直连网线（最简单，推荐）

- 用一根**普通网线**（千兆网口已支持自动翻转，无需交叉线）将两台机器的 LAN 口直连；
- 双方手动配置同网段静态 IP：
  - 爬虫机：`192.168.100.10 / 24`
  - 联网机：`192.168.100.20 / 24`
- 无需网关，无需 DNS，无需交换机；
- 关闭 Windows 防火墙的"专用网络"或开放 5000 端口。

```powershell
# 爬虫机执行（假设 LAN 网卡 ifIndex = 14）
New-NetIPAddress -InterfaceIndex 14 -IPAddress 192.168.100.10 -PrefixLength 24
New-NetFirewallRule -DisplayName "Spider API" -Direction Inbound -LocalPort 5000 -Protocol TCP -Action Allow
```

##### 方案 ②：小型交换机

- 适用于 3 台及以上设备（如多爬虫机并行）；
- 推荐 TP-LINK TL-SG105（5 口千兆，¥80 左右）；
- 同样静态 IP 即可。

##### 方案 ③：通信协议

- **HTTP REST API（推荐）**：爬虫机用 FastAPI/Flask 暴露：
  - `GET  /api/v1/data?since=2026-06-19T00:00:00`
  - `POST /api/v1/trigger`
  - `GET  /api/v1/health`
- **替代方案**：共享文件夹（SMB）、消息队列（局域网 RabbitMQ）；REST 最简单可观察。

#### 2.C.4 硬件需求清单 + 预算

| 项目 | 规格 | 数量 | 单价（元） | 小计 |
| --- | --- | --- | --- | --- |
| Windows 主机（爬虫机） | i5/8GB | 1 | 3500 | 3500 |
| Windows 主机（联网机，可用现有办公机） | i3/8GB | 1 | 2500 | 2500 |
| 4G 网卡（联网机用） | 华为 E3372h | 1 | 200 | 200 |
| 物联网 4G 卡（首年） | 30GB/月 | 1 | 240 | 240 |
| 网线（直连） | Cat6 1m | 1 | 10 | 10 |
| 小型交换机（可选） | TP-LINK SG105 | 0~1 | 80 | 0~80 |
| **合计** |  |  |  | **¥6450 ~ ¥6530** |

> 若联网机直接用现场办公电脑，可省 2500 元，预算降至 ~¥3950。

#### 2.C.5 优缺点

✅ **优点**
- **网络物理隔离最彻底**，符合电力行业等保要求
- 爬虫机故障不影响联网机的钉钉远程
- 可支持多爬虫机水平扩展
- 安全合规审计友好

❌ **缺点**
- 硬件成本翻倍
- 需协调两台机器位置
- 维护复杂度上升（双机配置、双机更新）
- 需要 IT 配合配置 IP

### 模式 D：纯离线保底方案（系统底座、必须内置）

> ⚠️ **本模式是系统的底座与基础，必须默认开启。A/B/C 都是在 D 的基础上叠加外网能力。**
>
> **核心原则**：D 模式只负责一件事——**把数据从交易平台爬下来，存到本地，并打成一个可拷走的压缩包**。上传交给人工。

#### 2.D.1 设计变更说明（对原方案的简化）

原方案中的 SQLite 离线队列、自动批量上传、断点续传等机制被取消，改为更贴近现场使用习惯的“**文件系统分层目录 + 台账 Excel + 任务级自动压缩包**”方案：

- 🔄 调整：**SQLite 仅用于任务状态追踪（运行时记录任务/指标的执行状态），不用于数据存储**。采集到的实际数据始终以 Excel 文件形式存储在文件系统中；
- ❌ 去掉：“自动批量上传缓存数据”、把数据塞进 SQLite 同步队列、后台 watchdog 自动出队上传；
- ✅ 保留：外网失联 → 自动降级到本地存储的能力；
- ✅ 新增：按年/月/日分层的本地目录结构、台账 Excel、任务级自动 zip 压缩包；
- ✅ 上传方式：**人工拷贝 zip 过去**（U 盘 / 邮件 / 内部网盘 都可以），不走程序自动上传。

#### 2.D.2 本地存储目录结构设计

数据根目录（`data_root`）由 `common.yaml` 统一配置，所有模式均写入同一位置。

```
data/                                          # 数据根目录（配置在 common.yaml 中）
├── 2026-01/                                   # 按年月分层
│   ├── 2026-01-15/                            # 按年月日分层
│   │   ├── 日清算采集_20260115_0830/          # 任务名_执行时间
│   │   │   ├── 台账.xlsx                      # 本次任务的台账文件
│   │   │   ├── 日前出清/
│   │   │   │   ├── 2026-01-14.xlsx
│   │   │   │   └── 2026-01-15.xlsx
│   │   │   ├── 实时出清/
│   │   │   │   └── 2026-01-15.xlsx
│   │   │   └── 日清算概览/
│   │   │       └── 2026-01-15.xlsx
│   │   └── 日清算采集_20260115_0830.zip       # 自动压缩包（与任务文件夹同级，方便转移）
│   │
│   └── 2026-01-16/
│       └── ...
└── 2026-02/
    └── ...
```

**设计要点：**

- 按 `年月 / 年月日 / 任务名_执行时间` 三级分层，方便检索与归档；
- 每个任务文件夹内部按 **指标名称**（日前出清、实时出清、日清算概览 …）分子文件夹，文件名以业务日期命名；
- 每个任务根目录下必须有一份 `台账.xlsx`，全面记录本次采集结果；
- zip 压缩包与任务文件夹 **同级**（都在当天日期目录下），人工拷贝时只拷 zip 一个文件即可。

#### 2.D.3 台账 Excel 设计

台账（`台账.xlsx`）是任务执行后的 **自动生成报告**，采集人员与现场查阅都以它为准。

##### Sheet1：文件清单

| 指标名称 | 文件路径 | 文件大小 | 状态 | 预期存在 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 日前出清 | ./日前出清/2026-01-15.xlsx | 128KB | ✅ 成功 | ✓ | |
| 实时出清 | ./实时出清/2026-01-15.xlsx | 0 | ❌ 缺失 | ✓ | 平台暂无数据 |
| 日清算概览 | ./日清算概览/2026-01-15.xlsx | 64KB | ✅ 成功 | ✓ | |

- **状态**列用颜色标识：
  - 🟢 绿色 = 成功
  - 🔴 红色 = 失败 / 缺失
  - 🟡 黄色 = 部分成功（多个日期中只下载到一部分）
- **预期存在**列用于区分“应该要但没有”与“本来就不要”；
- **备注**列记录错误原因、重试次数、页面异常提示等。

##### Sheet2：执行摘要（可选图表）

- 总文件数、成功数、失败数、成功率；
- 饼图（可选）展示成功 / 失败 / 部分成功 比例；
- 执行开始时间 / 结束时间 / 总耗时；
- 账号、任务名、模式（D）、调用人、机器名等环境信息。

#### 2.D.4 自动压缩机制

- 每次任务执行完毕后，**自动将整个任务文件夹打为 zip**；
- zip 名与任务文件夹同名（如 `日清算采集_20260115_0830.zip`）；
- zip 放在**当天日期目录下**（与任务文件夹同级）；
- 压缩包包含台账、所有指标文件，拷走一个 zip 即为本次采集的完整交付物；
- 人工拷贝路径：U 盘 / 移动硬盘 / 内部网盘 / 邮件附件，不限制传输方式。

#### 2.D.5 数据展示三层架构

系统采用“单一数据源、多层展示”的设计，确保数据一致性的同时满足不同场景的查看需求：

```
SQLite（运行时状态追踪）
    ↓ 任务结束后
    ├──→ 自动生成 台账.xlsx（文件交付，离线可查）
    └──→ 渲染 Web UI 图表（在线实时查看）
```

##### 第一层：SQLite 任务状态库（内部，运行时）

| 用途 | 说明 |
|------|------|
| 任务状态追踪 | 记录每次任务计划爬取哪些指标、每个指标的执行状态（待执行/进行中/成功/失败） |
| 断点续采 | 任务中断后重启时，通过 SQLite 知道哪些已完成、哪些需要重爬 |
| 幂等判断 | 同一天重复执行时，快速判断是否已爬过（比遍历文件系统快） |
| 历史聚合 | 支持跨任务的统计查询（历史成功率、数据完整性等） |

核心表设计（简版）：

```sql
-- 任务表
CREATE TABLE tasks (
    id TEXT PRIMARY KEY,
    name TEXT,              -- 任务名称（如"日清算采集"）
    created_at DATETIME,
    finished_at DATETIME,
    status TEXT,            -- pending/running/completed/failed
    config_file TEXT,       -- 使用的配置文件路径
    output_dir TEXT         -- 输出目录路径
);

-- 采集项明细表
CREATE TABLE task_items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id TEXT REFERENCES tasks(id),
    indicator_name TEXT,    -- 指标名称（如"日前出清"）
    target_date TEXT,       -- 目标日期
    status TEXT,            -- pending/success/failed/skipped
    file_path TEXT,         -- 生成的 Excel 文件路径
    file_size INTEGER,      -- 文件大小(bytes)
    error_msg TEXT,         -- 失败原因
    started_at DATETIME,
    finished_at DATETIME
);
```

> ⚠️ **注意**：SQLite 仅用于状态追踪，不存储实际采集数据。采集的数据始终以 Excel 文件形式存在文件系统中。

##### 第二层：台账 Excel（文件交付，离线可查）

每次任务执行完毕后，从 SQLite 中读取本次任务结果，自动生成 `台账.xlsx`：

- **生成时机**：任务全部执行完毕后自动生成；
- **存放位置**：任务文件夹根目录（如 `日清算采集_20260115_0830/台账.xlsx`）；
- **目标用户**：不使用数据库的运维人员、客户、管理者，双击即可查看。

Sheet 设计：

| Sheet | 内容 | 说明 |
|-------|------|------|
| 文件清单 | 指标名、文件路径、大小、状态(红绿)、预期存在、备注 | 主表，一眼看到什么有什么缺 |
| 执行摘要 | 总数/成功/失败、执行时间、耗时、成功率饼图 | 快速了解整体情况 |
| 异常明细 | 失败项的错误原因、重试次数、最后一次错误堆栈 | 排查问题用 |

Excel 格式增强：

- 状态列使用条件格式：绿底=成功 ✅，红底=失败 ❌，黄底=部分成功 ⚠️；
- 执行摘要 Sheet 包含 Excel 原生饼图（成功/失败/跳过占比）；
- 文件大小列包含数据条可视化。

##### 第三层：Web UI 图表（在线实时，增强分析）

通过 FastAPI 提供的 Web 页面展示，适用于联网模式（A/B/C）下的实时监控：

| 视图 | 数据来源 | 说明 |
|------|---------|------|
| 当前任务结果 | 实时读取 SQLite | 任务执行后立即可看，无需等生成 Excel |
| 历史采集趋势 | SQLite 聚合查询 | 按日/周/月维度查看采集成功率变化 |
| 数据完整性热力图 | SQLite task_items | 横轴=日期，纵轴=指标，颜色=有无数据 |
| 任务耗时分布 | SQLite tasks | 了解每次任务花多长时间，发现异常 |
| 系统状态仪表盘 | 实时监控数据 | WiFi 信号、Token 状态、下次任务时间 |

**与台账 Excel 的区别：**

- Excel 是静态快照（一次任务的定格），Web 是动态全局视图（跨任务聚合）；
- Excel 可以离线带走，Web 需要系统运行中才能看；
- 纯离线模式（D）下 Web UI 不可用，仅依赖台账 Excel。

##### 三层协作流程

```
任务开始
  → SQLite 记录: tasks.status = 'running'
  → 逐个指标执行
      → SQLite 更新: task_items 逐行写入状态
      → 数据文件落盘: Excel 写入文件系统
  → 任务结束
      → SQLite 更新: tasks.status = 'completed'
      → 自动生成: 台账.xlsx（从 SQLite 导出）
      → 自动压缩: 任务文件夹 → .zip
      → Web UI: 自动刷新展示最新结果
```

#### 2.D.6 最低硬件需求

| 项目 | 规格 | 数量 |
| --- | --- | --- |
| Windows 主机 | Win10，4 核 8GB | 1 台 |
| U-Key | 电力交易中心配发 | 1 个 |
| 移动存储 | U 盘 / 移动硬盘（用于拷贝 zip） | 1 个 |

#### 2.D.7 优缺点

✅ **优点**
- 零外网依赖，最强保底、最低保障线的实现
- 实现最简单：只需文件系统 + Excel，无需数据库同步逻辑
- 现场人员一看台账就知道采集是否完整，出问题可追溯
- 压缩包转运灵活，不依赖任何服务端接口
- 适合保密机房 / 完全隔离环境

❌ **缺点**
- 数据上传需人工转运，存在延迟（按班表周期）
- 钉钉远程、Agent 实时推送能力丧失
- 需人员定期拷压缩包

**推荐实施顺序**：

```
D（纯离线） → A/B（单机联网） → C（双机，视需要）
```

- **D 是基础**：先确保数据能爬能存能打包，这是不可妥协的底座；
- **A/B 在 D 基础上加联网能力**：D 跑通后再叠加钉钉远程、Agent 推送；
- **C 是最后考虑的高级模式**：仅在安全/合规明确要求物理隔离、或要多爬虫水平扩展时才上。

**保底原则**：所有模式都内置 **D 的离线落地能力**（本地目录 + 台账 + zip 压缩包），外网上传失败不影响本地采集。

### 5.1 设计哲学

### 5.2 模块化分层

```
┌──────────────────────────────────────────────────────────┐

│   └────────────┴────────────┴────────────┴────────────┘ │
（注：D 模式仅写本地文件系统 + 台账 Excel，SQLite 只用于任务状态追踪，不承载数据队列）
├──────────────────────────────────────────────────────────┤
```

### 5.3 多配置文件示例

```bash
# 启动示例
python main.py --config configs/mode_d_offline.yaml
python main.py --config configs/mode_a_wired.yaml
```

```yaml
# configs/common.yaml —— 公共配置（所有模式共享）

  log_dir:   "./logs"             # 日志路径
  ledger_template: "./templates/台账模板.xlsx"
  zip_pattern: "{task_name}_{yyyymmdd}_{HHMM}.zip"

platform:
  domain: "pm.gd.csg.cn"          # 交易平台域名
  login_url: "https://pm.gd.csg.cn/..."

schedule:
  default_timeout_sec: 300
  max_retry: 3
```

```yaml
# configs/mode_d_offline.yaml —— 纯离线保底
deployment:
  mode: D

  pronet:
    interface: "Wi-Fi"            # U-Key 网卡名
  internet:
    enabled: false                # D 模式不依赖外网
```

```yaml
    interface: "Wi-Fi"

  enabled: true
```

### 5.4 自动降级触发条件

| 触发条件 | 持续时间 | 动作 |
| --- | --- | --- |
| 外网连续 ping 失败 | > 60s | 上传切换为本地落地（数据写文件系统 + 台账 Excel；SQLite 仅记录任务/指标状态） |
| 路由表异常（专网走默认网关） | 立即 | 自动重新执行 `route add` 修复 |
| 上传重试 > 3 次失败 | — | 标记该指标状态为 failed（写入 SQLite task_items），等待人工或下一轮调度补采 |
| 外网恢复 | 连续 ping 成功 30s | 后台扫描 SQLite 中状态为 failed/pending 的指标进行补采 |
| 磁盘剩余 < 1GB | — | 告警并暂停采集 |

### 5.5 共享代码原则

- 所有模式共用同一 `spider-core` 包，**爬虫逻辑零差异**；
- 模式间差异只体现在 `transport/` 子模块（4 个适配器实现）；
- 切换模式：`pip install` 不变，只改 `config.yaml` + 重启服务。
