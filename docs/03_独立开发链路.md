# 广东电力交易数据智能采集系统 — 独立开发链路规划

> 文档版本：v1.0  
> 适用项目：spider-gd（广东电力交易数据智能采集系统）  
> 核心策略：**先搭框架骨架，再全链路并行开发**

---

## 1. 概述

### 1.1 为什么要按链路拆分

广东电力交易数据采集系统涉及 U-Key 网络配置、浏览器自动化、验证码识别、定时调度、SQLite 状态追踪、本地文件落地、告警推送、Agent 远程控制、健康监控等多个维度。如果按"自上而下一次性串行开发"的方式推进，会面临以下问题：

| 问题             | 后果                                                       |
| ---------------- | ---------------------------------------------------------- |
| **强耦合**       | 任何一处改动都可能波及全局，回归成本高                     |
| **串行阻塞**     | 一个开发者堵住，其余人无法推进                             |
| **联调成本高**   | 必须等所有模块都好了才能集成测试，问题暴露晚               |
| **现场依赖强**   | 部分功能（如 U-Key 网络）必须到现场才能测，开发期无法验证 |
| **难以独立交付** | 无法单独打包工具（如网络配置 exe）给运维使用               |

为此采用**链路化拆分**：把系统纵向切成 7 条链路，每条链路具备：

- **独立 I/O**：自身有清晰的输入输出边界
- **独立运行**：可单独启动、单独调试
- **独立测试**：通过 Mock 替代上下游，单元/集成测试自闭环
- **接口通信**：链路之间仅通过 `typing.Protocol` 定义的接口耦合，禁止直接 import 实现类

### 1.2 链路划分原则

1. **单一职责**：每条链路只负责一类问题域（采集 / 网络 / 调度 / 告警 / 监控）
2. **接口先行**：链路 0 优先定义所有 Protocol，下游链路依赖抽象而非具体实现
3. **可 Mock 化**：所有外部依赖（HTTP、文件、设备、webhook）必须可被 Mock 替换
4. **可独立交付**：链路 2（网络工具）可单独打包为 exe，链路 5（Agent）可拆卸
5. **逐步集成**：先单链路自测 → 双链路联调 → 全链路 E2E

## 3. 各链路详细设计

### 链路 0：项目骨架（最先完成，1-2 天）

#### 3.0.1 目标

搭建项目基础设施，确立目录结构、配置规范、日志规范、测试规范，**并定义所有跨链路 Protocol 接口**，让后续 6 条链路可以并行启动。

#### 3.0.2 内容清单

1. **目录结构创建**（参见第 7 章）
2. **依赖管理**
   - `pyproject.toml`（推荐，使用 PEP 621 元数据）
   - `requirements.txt`（备用，便于 pip 直装）

3. **全局日志配置（loguru）**
   - 控制台彩色输出 + 文件按日轮转
   - 日志级别可由环境变量控制
   - 提供 `from spider_gd.config.logging import logger` 统一入口

     - 提供开关：`log.persist_to_file: true/false`（在 `common.yaml` 中配置）
     - 本地路径可配：`log.file_dir: "./logs"`

     - 命名规则：`logs/{年月日}/{任务名}_{执行时间}.log`

   - 配置示例：
     ```yaml

     log:
       persist_to_file: true
       file_dir: "./logs"
       console_level: "INFO"
       file_level: "DEBUG"
       retention_days: 30
     ```

4. **配置系统（pydantic-settings）**

   - 分层配置：`AppSettings` / `CrawlerSettings` / `NetworkSettings` / `DingTalkSettings`

   - `interfaces/session.py` — `SessionManager`
   - `interfaces/fetcher.py` — `ApiFetcher`

   - `interfaces/scheduler.py` — `TaskScheduler`
   - `interfaces/notifier.py` — `Notifier`
   - `interfaces/network.py` — `RouteManager` / `UsbMonitor`
   - `interfaces/health.py` — `HealthChecker`
7. **统一入口骨架（main.py）**
   - 使用 `argparse` 或 `typer` 暴露子命令
   - `python main.py --help` 显示所有可独立运行的子模块
   - 子命令骨架（实现留空，由各链路填充）：
     - `crawl` — 链路1
     - `network` — 链路2
     - `schedule` — 链路3
     - `dingtalk` — 链路4
     - `serve` — 链路5

### 链路 1：爬虫核心引擎（核心价值，5-7 天）

#### 3.1.1 目标

实现从**登录 → 验证码识别 → 会话维护 → API 调用 → 数据获取**的完整采集流程。这是整个系统的核心价值所在。

#### 3.1.2 子模块

##### 1) `captcha_solver` — 验证码识别

- **职责**：使用 ddddocr 识别广东电力交易中心的数字验证码
- **输入**：`bytes`（验证码图片二进制）
- **输出**：`str`（识别出的数字文本）
- **接口**：`interfaces/captcha.py::CaptchaSolver`
- **关键实现点**：
  - 模型实例可复用（避免每次都加载）
  - 失败重试（识别置信度低时重新请求验证码）
  - 异常隔离（ddddocr 抛错不应中断整个流程）
- **Mock 策略**：`tests/fixtures/captcha_samples/` 下预存 20+ 张已知答案的验证码图片，单元测试断言识别率 ≥ 90%

##### 2) `session_manager` — 会话凭证管理

- **职责**：维护登录后的 Token、Cookie、`HdKGccbL` 等动态参数
- **输入**：Playwright `Page` 对象
- **输出**：可用于 HTTP 请求的 headers/cookies 字典
- **接口**：`interfaces/session.py::SessionManager`
- **关键实现点**：
  - 从浏览器上下文提取 cookies
  - 监听响应头/JS 变量提取 `HdKGccbL`
  - **412 过期检测** → 触发重登
  - **401 失败** → 抛出 `AuthFailedError`
  - 凭证持久化（可选，加密存储到 SQLite，避免每次重登）
- **Mock 策略**：使用 `pytest-httpx` 或 `responses` 模拟三种 HTTP 响应（200 正常 / 412 过期 / 401 失败）

##### 3) `api_fetcher` — 通用 API 采集引擎

- **定位**：**通用 HTTP API 调用引擎**，不含业务逻辑，对应架构图中的"后台采集(API)"方案
- **输入**：有效 session（Token / Cookie / `HdKGccbL`） + 任务配置（URL、参数、请求方式）
- **输出**：原始响应数据（Excel / JSON bytes）
- **接口**：`interfaces/fetcher.py::ApiFetcher`
- **核心原则**：具体爬取哪些接口、什么参数，由**任务配置**定义，**不硬编码在引擎中**
- **已知接口示例**（从同事代码中确认，仅作为配置参考，非引擎硬编码）：
  ```
  POST /pfjs/qctc-pm-jsgl-electricity-month-query/sbs/calDayStatQuery/exportItemsWithoutCalVersion
  参数: pdate=YYYYMMDD
  认证: Bearer Token + HdKGccbL + Cookie
  ```
  系统设计为**接口可配置**，后续确认更多接口后只需加配置不改代码
- **关键实现点**：
  - 使用 `httpx.AsyncClient`（保持长连接 + HTTP/2）
  - 超时 / 重试 / 限流策略
  - 响应内容嗅探（识别返回是 Excel 还是错误 HTML）
  - 接口元数据（URL、method、参数模板、认证模式）从 yaml/json 任务配置加载
- **Mock 策略**：`tests/fixtures/api_responses/` 预存真实 API 响应（脱敏后的 Excel + 错误响应）

##### 4) `playwright_runner` — 浏览器自动化引擎

- **职责**：管理 Playwright 浏览器生命周期，提供页面操作原语
- **输入**：任务配置（headless / proxy / user-data-dir 等）
- **输出**：已就绪的 `Page` / `BrowserContext` / 截图 bytes
- **关键实现点**：
  - 单例 BrowserContext，避免重复启动
  - 反检测配置（user-agent、viewport、`navigator.webdriver` 隐藏）
  - 异常自动截图保存（`logs/screenshots/`）
  - 资源拦截（block 图片/字体提速，可选）
- **Mock 策略**：开发期使用公开测试网站（如 `https://playwright.dev`）验证基本能力，无需依赖专网

##### 5) `login_flow` — 登录流程编排

- **职责**：**仅负责登录认证**，编排 `playwright_runner` + `captcha_solver` + `session_manager`，完成"账密 → 验证码 → 提交 → 校验 → 输出会话"全流程
- **输入**：用户名 + 密码 + 平台 URL
- **输出**：有效 session（包含 Token / Cookie / `HdKGccbL`）
- **重要边界**：**`login_flow` 不包含、不调用 `api_fetcher`**

**与 `api_fetcher` 的上下游关系**：

```
login_flow（登录流程）
  输入: 用户名 + 密码 + 平台URL
  输出: 有效session（包含Token/Cookie/HdKGccbL）
  职责: 仅负责登录认证，获取有效会话

api_fetcher（采集引擎）
  输入: 有效session + 任务配置（API地址、参数）
  输出: 采集到的数据(bytes)
  职责: 使用session调用API获取数据

关系: 上下游 — login_flow 产出的 session 是 api_fetcher 的输入
调度: 由 scheduler 编排 → 先确保 session 有效(login_flow) → 再执行采集(api_fetcher)
```

- **关键实现点**：
  - 状态机式编排（每步失败有明确恢复策略）
  - 整体超时控制（默认 60s）
  - 关键节点截图保留（用于失败排查）
  - 产出的 session 由 `session_manager` 持有，供 `api_fetcher` 通过依赖注入消费
- **Mock 策略**：把 `playwright_runner` Mock 成"立即返回带预置 cookies 的 Page"，验证编排逻辑

#### 3.1.3 依赖

- 仅依赖链路 0 的骨架（接口、日志、配置、pytest）
- **不依赖任何其他链路**

#### 3.1.4 验收标准

- [ ] 5 个子模块的单元测试全部通过，覆盖率 ≥ 70%
- [ ] 使用 Mock 能跑通 `login_flow` 产出 session，再由 `api_fetcher` 消费 session 产出 Excel bytes（上下游解耦验证）
- [ ] 在测试网站上能验证 `playwright_runner` 启动、截图、关闭无泄漏
- [ ] `python main.py crawl --date 20260101 --dry-run` 能模拟整个流程

#### 3.1.5 独立运行命令示例

```bash

python main.py crawl --date 20260101 --dry-run

# 真实采集（需要专网环境）
python main.py crawl --date 20260101 --user xxx --password xxx

# 仅测试登录

# 仅测试验证码识别
```

### 链路 2：网络自动配置工具（2-3 天）

#### 3.2.1 目标

U-Key（USB 随身 WiFi）插入后，**自动检测设备 → 自动配置路由表 → 验证双网络连通性**，让用户无需手动敲 PowerShell 命令。

#### 3.2.2 子模块

##### 1) `usb_monitor` — U-Key USB 设备检测

- **职责**：通过 WMI 轮询检测特定 USB 设备的插拔事件
- **关键实现点**：
  - 使用 `wmi` 库或 `pywin32` 的 `Win32_PnPEntity`
  - 通过 VID/PID 或设备名匹配 U-Key
  - 轮询间隔 2-3 秒（避免 CPU 占用过高）
  - 提供回调：`on_plug_in(device_info)` / `on_plug_out(device_info)`
- **Mock 策略**：模拟 WMI 查询结果（dict 列表），通过注入测试 fixture 切换"已插入/已拔出"状态

##### 2) `route_manager` — PowerShell 路由表配置

- **职责**：调用 PowerShell 添加/删除指定网段的静态路由，把 `pm.gd.csg.cn` 流量定向到 U-Key 网卡
- **关键实现点**：
  - 用 `subprocess.run(["powershell", "-Command", ...])` 调用
  - **必须以管理员权限运行**（在主程序启动时检查并提示 UAC 提权）
  - 命令封装：
    - `route add` / `route delete`
    - `Get-NetRoute` 列出当前路由
    - `Get-NetIPInterface` 检测 U-Key 网卡 ifIndex
  - 配置项：目标网段、子网掩码、网关、metric
- **Mock 策略**：把 `subprocess.run` 替换为返回预置字符串的 fake，验证命令拼接正确性

##### 3) `network_validator` — 双网络连通性验证

- **职责**：验证"公网正常 + 专网（pm.gd.csg.cn）可达"
- **关键实现点**：
  - `ping` / `tcping` 探测
  - `httpx.head()` 探测目标 URL 状态码
  - DNS 解析验证（专网 DNS 是否生效）
  - 输出结构化报告：`{public_ok: bool, private_ok: bool, latency_ms: int}`
- **Mock 策略**：Mock `httpx`/`socket` 调用

#### 3.2.3 依赖

- 仅依赖链路 0 的骨架
- **完全独立**，可单独打包

#### 3.2.4 验收标准

- [ ] 单元测试通过（Mock WMI / PowerShell）
- [ ] 在有 WiFi 的开发环境（无 U-Key）能跑通"假设设备已插入"的全流程模拟
- [ ] 可用 PyInstaller 打包为 `network_tool.exe` 独立运行
- [ ] 提供 GUI 或命令行两种模式（命令行优先）

#### 3.2.5 独立运行命令示例

```bash

python main.py network --monitor

# 手动配置路由（已知 U-Key 已插入）
python main.py network --configure

# 仅验证当前连通性
python main.py network --validate

# 打包为独立 exe
pyinstaller --onefile --uac-admin -n network_tool tools/network_tool_entry.py
```

### 链路 3：任务调度 + 数据存储（3-4 天）

#### 3.3.1 目标

定时任务执行 + **三层存储架构**（SQLite 状态追踪 + 文件系统数据落地 + Web UI 在线查看）。让爬虫"按时跑、跑完存、状态可查、数据可下载"。

**三层存储职责划分**：

| 层 | 用途 | 存储内容 |
| --- | --- | --- |
| **SQLite** | **仅状态追踪** | 任务执行状态（哪些指标已爬/未爬/失败）、断点续采、幂等判断；**不存储实际数据** |
| **文件系统** | **数据存储** | 采集数据以 Excel 文件存储，按 `{年月}/{年月日}/{任务名}_{执行时间}/{指标名}/` 组织；自动生成台账.xlsx + zip 压缩 |
| **Web UI** | **在线查看** | 从 SQLite 读取状态渲染图表，提供历史趋势、完整性热力图 |

#### 3.3.2 子模块

##### 1) `task_scheduler` — APScheduler 调度器

- **职责**：定时触发爬虫任务 + 提供手动触发接口
- **关键实现点**：
  - 使用 `BackgroundScheduler`（非阻塞）
  - 支持 cron 表达式（如 `0 9,15 * * *`）
  - 手动触发接口：`scheduler.trigger_now(task_id)`
  - **失败重试（指数退避）**：1min → 5min → 15min → 60min，最多 4 次
  - JobStore 使用 SQLite（与业务库分离），重启不丢任务
- **Mock 策略**：使用 APScheduler 自带的 `MemoryJobStore` + 加速时钟测试

##### 2) `storage_manager` — SQLite 状态追踪

- **职责**：**仅记录任务执行状态**，不存储实际采集数据；支持断点续采、幂等判断
- **核心边界**：实际 Excel/JSON 数据落地到文件系统，由 `local_landing` 负责；SQLite 只存"指针"和"状态"
- **表设计**：

  | 表名             | 说明                                                |
  | ---------------- | --------------------------------------------------- |
  | `tasks`          | 任务定义（id、name、cron、target_date、enabled） |
  | `crawl_status`   | 采集状态（id、task_id、pdate、item_code、status[pending/running/success/failed]、file_path、error_msg、updated_at） |
  | `execution_log`  | 执行历史（id、task_id、started_at、finished_at、result_summary、log_file_path） |

- **关键实现点**：
  - 使用 `sqlite3` 标准库 + 轻量 DAO 封装（不引入 ORM 重型依赖）
  - **WAL 模式**：`PRAGMA journal_mode=WAL`，提升并发读写
  - 索引：`crawl_status(pdate, item_code)`、`crawl_status(status)`
  - 幂等判断：执行前查 `crawl_status`，跳过已 success 的指标
  - 断点续采：失败的指标保留 status=failed，下次执行可只重试这些
  - 数据库迁移脚本：`migrations/V1__init.sql`
- **Mock 策略**：使用 `:memory:` 内存数据库做单元测试

##### 3) `data_processor` — 数据清洗 / 去重 / 补漏

- **职责**：对采集到的 Excel 数据进行清洗、按主键去重、检测时间序列缺口
- **关键实现点**：
  - 使用 `pandas` 读取 Excel
  - 主键定义：`(pdate, time_slot, item_code)`
  - 缺口检测：扫描 `crawl_results.pdate`，对比预期日期范围，生成补采任务列表
  - 去重策略：`INSERT OR REPLACE` 或显式 SELECT-then-INSERT
- **Mock 策略**：构造 pandas DataFrame fixture

##### 4) `local_landing` — 本地文件落地管理

- **职责**：管理采集数据在本地文件系统的落地、台账生成与归档压缩
- **目录结构**：
  ```
  data/
  └── {年月}/                    # 例: 2026-01/
      └── {年月日}/               # 例: 2026-01-15/
          └── {任务名}_{执行时间}/  # 例: 日清算采集_20260115_083000/
              ├── {指标名1}/      # 例: 节点电价/
              │   └── *.xlsx
              ├── {指标名2}/
              │   └── *.xlsx
              ├── 台账.xlsx       # 自动生成（红绿状态 + 图表）
              └── ...
  archives/
  └── 日清算采集_20260115_083000.zip   # 任务完毕自动压缩
  ```
- **关键实现点**：
  - **目录结构创建**：根据任务配置自动建立年月/年月日/任务名层级
  - **Excel 落地**：`api_fetcher` 输出的 bytes 写入对应指标目录
  - **台账生成**：基于 SQLite 中本次执行的状态生成 `台账.xlsx`，红绿单元格标识每个指标的成功/失败
  - **zip 压缩**：任务完毕后将整个任务文件夹压缩为 zip 归档
  - **路径登记**：每个 Excel 文件的相对路径写入 `crawl_status.file_path`
- **Mock 策略**：使用 `tmp_path` fixture 验证目录创建、台账生成、zip 压缩流程

#### 3.3.3 依赖

- 依赖链路 0 骨架
- 依赖链路 1 的 `ApiFetcher` Protocol（**通过 Mock 解耦**）

#### 3.3.4 验收标准

- [ ] 调度器能独立运行，cron 触发 Mock 任务正常

- [ ] 单元测试覆盖率 ≥ 70%

### 链路 4：告警网关（Alert Gateway）（1-2 天）

#### 3.4.1 目标

提供**统一的告警推送能力**，任何模块都能一行代码发通知。

#### 3.4.2 核心设计

- 本质就是 `send_alert(channel, level, message)` 接口
- 通过配置面板设置告警通道（钉钉群 webhook / 飞书 webhook / 邮件 / 企业微信）
- **不接收指令，只发送通知**（单向推送）

#### 3.4.3 子模块

##### 1) `alert_gateway` — 统一告警接口

- **职责**：路由到具体通道
- **输入**：告警级别（INFO / WARN / ERROR） + 消息内容
- **输出**：发送结果（成功 / 失败）

##### 2) `webhook_sender` — HTTP webhook 调用

- **职责**：钉钉 / 飞书 / 企业微信群机器人
- **配置**：webhook URL + 签名密钥

##### 3) `email_sender` — 邮件发送（可选，SMTP）

##### 4) `alert_config` — 告警配置管理

- **配置项**：哪些事件触发告警、发到哪个通道、静默时间段

#### 3.4.4 配置示例

```yaml
# common.yaml 或 alert 专用配置
alert:
  channels:
    - type: dingtalk_webhook
      url: "https://oapi.dingtalk.com/robot/send?access_token=xxx"
      secret: "SECxxx"
      events: [error, task_failed, ukey_disconnected]
    - type: email
      smtp_host: "smtp.example.com"
      to: ["admin@example.com"]
      events: [error]
  silence_window: "23:00-07:00"  # 静默时段不告警
```

#### 3.4.5 依赖

- 仅依赖链路 0 骨架
- **极简设计**：只需 webhook 调用能力

#### 3.4.6 Mock 策略

Mock HTTP 请求，验证消息格式和路由逻辑。

#### 3.4.7 验收标准

- [ ] 调用 `send_alert` 后钉钉群收到消息
- [ ] 多通道路由正确（根据事件类型分发）
- [ ] 静默时段内告警被正确抑制
- [ ] 单元测试覆盖率 ≥ 70%

#### 3.4.8 独立运行命令示例

```bash
# 测试告警发送
python -m spider_gd.gateway.alert --test "测试告警消息"

# 指定通道发送
python -m spider_gd.gateway.alert --channel dingtalk --level ERROR --message "任务失败"
```

### 链路 5：远程控制 Agent（Remote Agent）（3-5 天）

#### 3.5.1 目标

**可拆卸的高级功能模块**——通过 AI Agent 远程控制和监管整个爬虫系统。

#### 3.5.2 核心设计

- 这是一个**完全可选的模块**，移除后系统照常运行
- 接入方式：OpenClaw / Hermes Agent（通过微信 / 钉钉等 IM 双向交互）
- 本质：接收自然语言指令 → 解析为系统操作 → 执行 → 反馈结果

#### 3.5.3 功能分级（安全三级）

| 级别 | 权限 | 操作示例 | 交付时默认 |
| ---- | ---- | -------- | ---------- |
| **只读** | 查询状态 | 查各链路状态、查日志、拿台账文件、查历史记录 | 开放 |
| **配置** | 修改配置 | 改 cron 时间、改爬取范围、重新触发任务 | 需确认 |
| **系统** | 系统操作 | OTA 升级（git pull + 重启）、修改核心文件、重启服务 | 锁死（开发者用） |

#### 3.5.4 子模块

##### 1) `agent_adapter` — OpenClaw / Hermes Agent 适配层

- **输入**：自然语言指令（来自微信 / 钉钉）
- **输出**：执行结果文本 / 文件

##### 2) `command_executor` — 指令解析与执行

支持的指令类别：

- **自检**："检查系统状态" → 调用各模块 health_check
- **查询**："最近一次爬取结果" → 读 SQLite + 发送台账
- **控制**："立即爬取今天数据" → 触发 scheduler
- **文件**："发送昨天的日前出清数据" → 找到文件返回
- **配置**："把爬取时间改为每天 9 点" → 修改 yaml 重载
- **升级**："拉取最新代码" → git pull + restart（高危）

##### 3) `permission_guard` — 权限控制

- **职责**：根据操作级别判断是否允许执行、是否需要二次确认

##### 4) `response_formatter` — 结果格式化

- **职责**：将系统输出转为用户友好的文本 / 图表

#### 3.5.5 依赖

- 链路 0 骨架
- 链路 6 监控接口（用于自检，可 Mock）

#### 3.5.6 Mock 策略

模拟 Agent 消息输入，验证指令解析和权限控制。

#### 3.5.7 验收标准

- [ ] 通过模拟消息能正确执行查询类指令并返回结果
- [ ] 权限控制生效：默认锁死的系统级操作被拒绝
- [ ] **可拆卸验证**：配置禁用 agent 后系统启动不加载该模块，不影响主流程

> **注意**：此模块是**可拆卸的**，系统启动时通过配置决定是否加载。

#### 3.5.8 独立运行命令示例

```bash
# 启动 Agent 接入服务
python main.py agent --start

# 模拟指令测试
python main.py agent --simulate "检查系统状态"
```

#### 3.6.2 子模块

## 6. 集成策略

### 6.1 集成原则

1. **接口先行**：所有跨链路调用必须经过 `interfaces/` 下的 Protocol，**禁止直接 import 实现类**
2. **依赖注入**：在 `main.py` 中统一组装具体实现到 Protocol，便于切换 Mock / 真实实现
3. **单点配置**：所有配置由 `pydantic-settings` 统一管理，避免散落

### 6.2 集成顺序

```
Step 1: 0 → 1
        验证爬虫能独立产出 Excel bytes（login_flow 产出 session、api_fetcher 消费产出数据）

Step 2: 0 → 1 → 3
        把爬虫产出接入调度+三层存储，跑一次"调度触发→爬虫执行→文件落地→SQLite状态更新→台账生成→zip"

Step 3: 0 → 4
        独立验证告警网关，调用 send_alert 后钉钉群收到消息

Step 4: 0 → 6 + 4
        集成系统监控 → 告警网关，验证异常检测能触发告警

Step 5: + 5（可选，可拆卸高级模块）
        加入远程 Agent，验证自然语言指令 → 查询/控制/自检 闭环

Step 6: + 2（最后接入）
        现场环境验证 U-Key 网络配置 + 全链路真实采集
```

### 6.3 集成测试要点

- **冒烟测试**：每集成一步运行一次端到端冒烟（5 分钟内可完成）
- **回归测试**：单链路单元测试在集成阶段必须保持 100% 通过
- **性能基线**：单次采集端到端 ≤ 30s，调度器内存占用 ≤ 200MB
- **故障注入**：测试网络断开、Token 过期、SQLite 锁、webhook 调用失败等异常场景下系统能否优雅降级
- **日志审计**：集成阶段每条链路必须输出 traceId，便于跨链路追踪

## 附：开发自检清单

每条链路完成后请逐项确认：

- [ ] 所有公共 API 都对应 `interfaces/` 中的 Protocol
- [ ] 所有外部依赖（HTTP、文件、设备、webhook）都可 Mock
- [ ] 单元测试覆盖率 ≥ 70%
- [ ] 关键路径有 loguru 结构化日志（含 traceId）
- [ ] 日志按执行次数独立存储启用（`logs/{年月日}/{任务名}_{执行时间}.log`）
- [ ] login_flow 与 api_fetcher 解耦（上下游关系，不互相包含）
- [ ] api_fetcher 接口从任务配置加载，无硬编码
- [ ] SQLite 仅存状态，数据落地到文件系统，台账与 zip 自动生成
- [ ] 告警统一走 send_alert 接口，不直接调用具体通道 SDK
- [ ] 远程 Agent 可通过配置拆卸，拆卸后主流程运行不受影响
- [ ] 异常场景有明确处理（重试 / 降级 / 告警）
- [ ] 配置项全部从 `pydantic-settings` 读取，无硬编码
- [ ] `python main.py <子命令> --help` 能查看用法
- [ ] README 中有"如何独立运行/独立测试"章节
- [ ] 与其他链路的集成点已用 Mock 验证
